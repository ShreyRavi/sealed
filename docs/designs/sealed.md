# Design: Sealed, phrase-locked secret messages with no backend

Generated by /office-hours on 2026-11-01
Branch: main
Repo: ShreyRavi/sealed
Status: APPROVED
Mode: Builder

## Problem Statement

People send secrets (gate codes, account recovery codes, Wi-Fi passwords, addresses) through chat apps that keep them forever: in provider logs, in phone backups, in screenshots. Sealed lets the sender encrypt the message on their own device with a key derived from a spoken phrase. They paste the resulting link into any chat and say the phrase on a call. The recipient taps the link, types the phrase, and the message decrypts locally. Nothing in between is trusted: no server, no account, no database, no logs.

Canonical home: `https://sealed.kansoboard.com`.

## What Makes This Cool

- **The second channel is the product.** "Say the phrase to open" turns a crypto tool into a small ritual between two people on a call. The chat app carries a puzzle; the voice carries the key.
- **The link preview proves the claim.** Every link unfurls to the same generic card because the fragment never reaches the host. No extra copy is needed to explain it.
- **Nothing secret ever leaves the phone, and that's checkable.** No request ever carries the phrase, message or payload, and after the first visit the page touches the network not at all.

## Constraints

- Static site only: one HTML entry, JS, and WASM (embedded in JS by hash-wasm). No API routes, no serverless functions, no analytics, no third-party scripts. A second static page, `threats.html`, is allowed.
- Payload lives only in the URL fragment.
- **Network promises (eng review OV4, D13), two of them:**
  1. **No request ever carries anything typed or received.** No phrase, message or payload, at any time, from the page, the KDF worker or the service worker. `connect-src 'none'` on documents and the worker backs this up.
  2. **Once cached, no network requests.** After the service worker controls the page and precache has finished, every request (KDF worker respawns included) is served from cache. On a first visit, the service worker's precache requests for static files do show in DevTools; they carry no user data.
  - The app is **ready** after `load` and the KDF worker's `ready` message (exposed as `data-ready="1"`, meaning the *current* worker is ready: it is "0" on Sealed and Revealed and while respawning, ROV7). Seal and Open stay disabled until then. Fonts are preloaded with `as="font" type="font/woff2" crossorigin`.
  - Open screen footnote 02: "Nothing you type or receive is ever sent anywhere. After the first visit, this page makes no network requests at all."
- No localStorage, sessionStorage, IndexedDB or cookies. Service worker Cache Storage holds static assets only, never user data.
- Vite + vanilla TypeScript, Vitest, Playwright. Exact-pinned dependencies, committed lockfile, pinned Node (`.nvmrc` + `engines`).
- `build.minify: false`, which is the plain reading of "no minification tricks". The bundle stays small enough that this costs little.
- Local CI/CD only, per the user's global rule: an `npm run ci` script, a dependency-free `.githooks/pre-push`, and `npm run deploy` (ci, then `wrangler pages deploy dist`). No GitHub Actions, and no Cloudflare-side builds (D14).
- Visual tokens from the PRD: ground #0B0F14, panel #141A22, border #243040, text #E6EDF5, muted #8A9BB0, mint #5EE0B3 (text on mint #06251B), amber #F2B84B on #2A1E14. Inter and JetBrains Mono, self-hosted woff2. Inline stroke SVG icons. 44px minimum touch targets. Real form elements only.
- Wireframe: none. The user-supplied hi-fi artboards are the design (canvas "Sealed: phrase-locked messages": Compose, Sealed, Chat thread, Open, Revealed, How it works, Threat model).

## Premises (agreed)

1. **Fragment-only transport.** The chat app is the only carrier. No server feature of any kind, including link shortening.
2. **Phrase floor of 50 bits (revised after the second opinion).**
   - Generated phrases are 4 distinct EFF large-list words, 51.7 bits, and always pass.
   - Custom phrases count every distinct qualifying token as a human-chosen word worth 10 bits, whether or not it is on the EFF list. Repeats, keyboard or alphabet runs, and denylisted phrases count 0. A custom phrase needs 5 distinct words. Length times character set is never used.
   - A phrase that loses letters during normalization is refused (for example Cyrillic, or "café" becoming "caf").
   - The estimator is in-house; zxcvbn is too large to audit.
3. **CSP, written out in full:**

   ```
   default-src 'self'; script-src 'self' 'wasm-unsafe-eval'; worker-src 'self';
   connect-src 'none'; img-src 'self'; font-src 'self'; style-src 'self';
   manifest-src 'self'; base-uri 'none'; form-action 'none'; object-src 'none';
   frame-ancestors 'none'
   ```

   - The real header comes from Cloudflare `_headers`, with **two path rules**:
     - `/*` gets the policy above. That covers documents and the KDF worker script, which needs `'wasm-unsafe-eval'` itself.
     - `/sw.js` gets the same policy with **`connect-src 'self'`** in place of `'none'`, plus `Cache-Control: no-cache`. A service worker runs under its own script's CSP, and `cache.addAll()` and its fetch handler need `connect-src`. Cloudflare merges every matching rule, so the `/sw.js` rule must begin with `! Content-Security-Policy` to drop the inherited `/*` policy. The header check requires exactly one policy on `/sw.js` (eng review OV1).
   - A `<meta>` tag placed before any script mirrors the document policy, except `frame-ancestors`, which only works in the header.
   - The E2E serves `dist/` with `wrangler pages dev` (exact-pinned devDependency), so `_headers` is applied in tests and a misapplied rule fails the offline test.
4. **Deploy.** Cloudflare Pages only, as a Direct Upload project: `npm run deploy` runs `npm run ci`, then `wrangler pages deploy dist`, so the tested `dist/` is exactly what ships. No Cloudflare-side builds. The API token lives only in the local environment (eng review OV5, D14). No GitHub Pages config, because its deploy path is Actions and it can't set headers.
5. **Hygiene is best-effort and documented.**
   - Zeroed: derived key bytes, normalized phrase bytes, and plaintext byte buffers.
   - Not zeroable: JS strings (`input.value`) and hash-wasm's internal memory.
   - `replaceState` cleans the URL bar and the tab's history entry. It may not remove the browser's global history or synced-history record.
6. **No timestamp in the payload.** Revealed shows "N characters · opened with your phrase".
7. **Message limit is 2000 Unicode code points**, so at most 8000 UTF-8 bytes.

## Cross-Model Perspective

Codex isn't installed, so a fresh Claude subagent did a cold read without this conversation. Its main points:

- **Coolest unconsidered version:** links that point at a verifiable build (a build hash shown in the UI, a reproducible build, a single-file `sealed.html`), so users trust an audited artifact, not a host. Also "reply under the same phrase" as a short-lived two-way channel.
- **What excites the builder:** `og:description "Say the phrase to open"`. The voice ritual is the product.
- **Closest existing tool:** hat.sh (static, client-side Argon2id, offline). The missing half is fragment transport, the payload format, the phrase generator, the voice-first UX, the strict CSP and the link-length work.
- **Challenged premise:** #2. A 40-bit floor with a gameable estimator is too weak for ciphertext that lives in chat logs forever. **Accepted:** the premise was revised to 50 bits with dictionary-only scoring.
- **Other findings taken into Approach B:**
  - The PBKDF2 fallback downgrades iOS Lockdown Mode users (High).
  - Long links fail silently in some apps (High).
  - Ciphertext length reveals message length (Medium).
  - Fragment read timing and retries (Medium).
  - Cloudflare preview deploys and script injection (Medium).
  - AAD should cover the full header (Low).
  - The "SEALED1" prefix next to a v2 byte is confusing (Low).
- **Rejected:** my proposed spoken link fingerprint. The reviewer was right that it defends against nothing: a swapped link fails anyway, and a phishing host shows the correct fingerprint. Compression before encryption was also skipped: it saves little on short messages and gives up the fixed padding sizes.

## Approaches Considered

- **A: Spec-exact.** The PRD as written, with a PBKDF2 v2 fallback. Rejected: Lockdown Mode users would get weaker links, message length leaks, and long links fail without warning.
- **B: Hardened spec.** Chosen. Details below.
- **C: Verifiable artifact (B plus published build hashes, build hash in the UI, single-file `sealed.html`).** Originally deferred to v1.1; pulled into v1 by eng review D19.

## Recommended Approach: B, hardened spec

### Crypto parameters (version 1)

- **Normalize:** `s.normalize('NFKC').toLowerCase()`, then keep `[a-z0-9]`, then UTF-8 encode. Mark the phrase lossy if any `\p{L}` or `\p{N}` character was dropped.
- **KDF:** Argon2id with m = 65536 KiB, t = 3, p = 1, a 16-byte salt from `crypto.getRandomValues`, and a 32-byte output.
  - Engine order: hash-wasm, then `@noble/hashes/argon2` if WASM can't compile.
  - Both engines must produce the same key for every test vector.
  - The raw key is imported as a non-extractable AES-GCM `CryptoKey`, and the raw bytes are then zeroed.
- **Cipher:** AES-256-GCM via WebCrypto, a 12-byte random nonce, a 128-bit tag, and AAD = header.
- **Payload:** `0x01 ‖ salt(16) ‖ nonce(12) ‖ ciphertext+tag`, base64url with no padding. The minimum valid length is 1 + 16 + 12 + 256 + 16 bytes.
- **Link:** `https://sealed.kansoboard.com/#<b64url>`. Plain-text form: `SEALED1 <b64url>`. The 1 names the text format; the byte inside sets the crypto version, and the docs say so.
- **Parser:** accepts a full link, a bare `#…`, the `SEALED1 …` form, and stray whitespace or line breaks inserted by chat apps.

### Crypto module API (`src/crypto/index.ts`)

Public surface (eng review A1). Nothing else is re-exported, and `tests/unit/architecture.test.ts` fails if `src/ui/` or `src/boot/` imports anything under `src/crypto/` other than `index`.

```ts
export const MAX_CHARS = 2000;             // code points

export type Derive = (phrase: Uint8Array, salt: Uint8Array) => Promise<CryptoKey>; // must zero raw key bytes
export type SealError = 'empty' | 'too-long' | 'weak-phrase' | 'phrase-lossy';
export interface Sealed { encoded: string; link: string; plain: string }
export function seal(message: string, phrase: string,
                     deps: { derive: Derive; random?: (n: number) => Uint8Array; lastSuggested?: string | null }) // calls estimate(phrase, lastSuggested) (eng review Q1)
  : Promise<{ ok: true; sealed: Sealed } | { ok: false; error: SealError }>;

export type OpenFailure = 'malformed' | 'unsupported-version' | 'didnt-open';
export function open(payload: Uint8Array, phrase: string, deps: { derive: Derive })
  : Promise<{ ok: true; message: string; chars: number } | { ok: false; reason: OpenFailure }>;

export function parseInput(input: string): Uint8Array | null; // link | #frag | SEALED1 form
```

Internal modules (imported only inside `src/crypto/` and by tests):

```ts
// kdf.ts: VERSION = 0x01, RESERVED_VERSIONS = [0x02]
export type KdfEngine = 'wasm' | 'js';
export function deriveKey(phrase: Uint8Array, salt: Uint8Array, engine: KdfEngine): Promise<CryptoKey>; // zeroes raw bytes
export function detectEngine(): Promise<KdfEngine>;
// kdf-client.ts: main-thread side of kdf.worker.ts; KdfClient.derive satisfies Derive (transfer in, transfer out, zeroize)
// payload.ts: BUCKETS, encodePayload/decodePayload, pad/unpad (ISO/IEC 7816-4)
// bytes.ts: b64urlEncode/b64urlDecode, wipe
// cipher.ts: AES-256-GCM seal/open with AAD = header
```

`src/phrase/`:

- `suggestPhrase(words = 4): string`: picks 4 distinct words from the **filtered** EFF list with `getRandomValues` and rejection sampling, so there is no modulo bias. The filter drops entries with non-letter characters and the homophones in `scripts/wordlist-excludes.txt`, leaving N words. Bits = log2(N·(N−1)·(N−2)·(N−3)), computed from N rather than hardcoded (≈ 51.6–51.7). A unit test asserts ≥ 50 (eng review OV7, D16).
- `estimate(phrase: string, lastSuggested: string | null): { bits: number; words: number; generated: boolean; ok: boolean; level: 0|1|2|3|4 }`.

**Estimator algorithm** (the Seal gate depends on it):

1. **Tokenize the raw input.** Apply NFKC and lowercase, then split on every run of characters outside `[a-z0-9]`. No segmentation is attempted: "copperlanternninejuniper" is a single non-dictionary token.
2. **Generated phrase.** If the input's normalized tokens equal those of `lastSuggested` (`tokens(input).join(' ') === tokens(lastSuggested).join(' ')`, so case, spaces and hyphens are ignored; eng review Q2; `lastSuggested` is kept in memory only), then `generated = true`, each word counts 12.9 bits, the total is 51.7, and the phrase passes. Any edit makes it a custom phrase.
3. **Custom phrase scoring.** Every token is treated the same way, whether it's on the EFF list, a name, a number or anything else.
   - A token **qualifies** if it has at least 3 characters and at least 3 distinct characters, and is not a run. A run means each character follows the previous one in `0123456789`, `abcdefghijklmnopqrstuvwxyz`, `qwertyuiop`, `asdfghjkl` or `zxcvbnm`, in either direction (so "qwert" and "1234" are runs).
   - Each **distinct** qualifying token counts **10 bits**, which discounts human choice. A repeated token counts 0.
   - A phrase on a small built-in denylist (e.g. "correct horse battery staple") counts 0 in total.
   - So any custom phrase needs 5 distinct words: "jennifer london soccer" = 30 bits, refused; "qwert qwert qwert" = 0 bits, refused.
4. **No per-character credit.** A long random password-manager string is one token worth 10 bits and is refused. That's deliberate, because the phrase has to survive being said out loud.
5. **Gate:** `ok = bits >= 50`.
   - Refusal copy: "Too easy to guess offline. Use 5 of your own words, or tap Suggest one."
   - Labels: generated shows "Strong: 4 random words ≈ 52 bits"; custom shows "Custom: ≈ N bits".
6. **Bar.** `level` is the number of lit segments: 0 for empty input, 1 below 25 bits, 2 below 38, 3 below 50, 4 at 50 or more.

Error rules:

- A failed GCM tag check and bad padding both return `didnt-open`, which renders only "Didn't open".
- `malformed` renders "This link is damaged or incomplete". `unsupported-version` renders "This link needs a newer version of Sealed".
- None of these messages say anything about the phrase.

### Screen behavior beyond the artboards

- **Routing.** If a fragment is present, the app shows Open; otherwise it shows Compose. There are no fragment-based routes. The threat model is built from `threats.html` and linked as `/threats`, because Pages redirects `.html` URLs with a 308 (eng review OV2).
- **Fragment capture.** It runs in the first module before anything else, and again on every `hashchange` event. That covers a second link opened in the same tab or in the installed PWA window. Each capture:
  1. parses the fragment,
  2. holds the payload in memory,
  3. calls `replaceState` to strip the URL,
  4. **cancels any in-flight Seal or Open**: increments an operation generation counter so stale results are dropped, terminates the KDF worker and starts a fresh one, and clears the busy state,
  5. calls `wipeAll()` on any current state (including a revealed message),
  6. switches to Open.

  The payload stays in memory, so a mistyped phrase can be retried without the link. A page reload loses the payload, and the UI says so ("Tap the link again").
- **The KDF runs in a dedicated module worker** (`src/crypto/kdf.worker.ts`, created with `new Worker(new URL(...), { type: 'module' })`, precached).
  - The phrase bytes are transferred to the worker, which detaches them on the main side.
  - The worker returns the raw key bytes as a transfer. The main thread imports them as a non-extractable `CryptoKey`, then zeroes them. The worker zeroes its copies too.
  - **Busy state.** On Seal or Open, the button shows a spinner and "Deriving key…", and every input and button is disabled. Only one operation can run at a time, so double taps do nothing.
  - If the operation passes 3 seconds on the JS engine, the copy changes to "Still working: this browser blocks the fast engine, so this can take a while."
  - **Lifetime (eng re-run RR2).** The worker is terminated on entering Sealed or Revealed, which never derive, freeing about 64 MiB while the sender is on the call. It respawns on entering Compose or Open (served from the service-worker cache once cached). Seal and Open stay disabled until the new worker reports ready.
  - **Spawn failure (eng re-run ROV1, ROV7).** `ensureWorker()` is the only spawner, and a stale `ready` is ignored. A worker `error` event or no `ready` within 10 s counts as a spawn failure: one automatic retry, then stop. The UI then shows an amber box, "Sealed was updated while this page was open. Reload to continue.", with a primary Reload button (a prefilled reply phrase is lost, and the copy says so). `public/404.html` makes Pages return a real 404 for a missing asset instead of index.html.
  - **Failure (eng review A2).** `KdfClient.derive` rejects on a worker `error` or `messageerror` event, on a failure message the worker posts (including a RangeError from the 64 MiB allocation), and when a 120 s per-derivation watchdog expires. On failure it terminates and respawns the worker. The UI clears the busy state, re-enables controls, and shows "Couldn't derive the key on this device. Close other tabs and try again." (or, for the watchdog, "This took too long. Try again or use another device."). `KdfClient` takes a worker factory: production passes `() => new Worker(...)`, and unit tests pass a fake.
- **Input attributes (eng re-run ROV2, ROV11).** The message textarea and both phrase inputs carry `spellcheck="false" autocorrect="off" autocapitalize="off"`. The phrase inputs also carry `autocomplete="off"`; Compose's phrase stays `type="password"` with the show toggle. This stops browser cloud spellcheck (Chrome Enhanced Spell Check, Microsoft Editor) from sending typed text, which network promise 1 requires. Every submit handler calls `preventDefault()` first.
- **Message limit.** No `maxlength` on the textarea, because it counts UTF-16 units. The counter and `seal()` count code points (`[...text].length`). Over 2000 the counter turns amber and Seal is disabled.
- **Navigation (design review D3, D4).**
  - Compose, Open and Revealed each end with a muted 12px footer link, "What it protects against", to `/threats`. It opens in a **new tab** (`target="_blank" rel="noopener noreferrer"`) so an unopened message or a draft survives. `sealed.html` links to the canonical `/threats`, also in a new tab (eng re-run RR1). `/threats` has a "Back to Sealed" link to `/`. In an installed standalone PWA the new tab opens in the system browser, which may not have `/threats` cached offline (ROV8, documented in SECURITY.md).
  - The Sealed screen's top-left control is a 44px text button "New message" (plus icon) to an empty Compose, replacing the artboard's back chevron, because the draft is already wiped.

```
            ┌──────────── /threats ◄── footer link (Compose, Open) ──┐
            │  "Back to Sealed" → /                                  │
            ▼                                                        │
  / (no fragment) ── Compose ── Seal ──► Sealed ── "New message" ──► Compose
        │   └ "Have a SEALED1 text? Open it" ──► Open (paste mode) ── "Write a new message" ──► Compose (ROV5)
```

- **Paste to open.** Compose has a "Have a SEALED1 text? Open it" link, and the Open screen accepts a paste when it has no fragment. If someone pastes a sealed link or SEALED1 text into the Compose textarea, the app offers "This looks like a sealed message. Open it?"
- **Strength bar.** The four segments correspond to under 25, under 38, under 50, and 50 or more bits. Below 50 the bar is amber and Seal is disabled, with the reason shown. Label: "Strong: 4 random words ≈ 52 bits".
- **Link-length meter** on the Sealed screen. Above 2000 characters it warns: "Long link: some apps cut it. Use the plain-text version."
- **Phrase to say on the call (design review D9).** The Sealed screen adds a neutral box under the link panel, "Phrase to say on the call", with a 44px "Show" / "Hide" toggle. Hidden by default; when shown, the phrase appears in 20px JetBrains Mono #E6EDF5. Its references are dropped when the sender leaves the screen: in-app navigation ("New message"), a `hashchange`, or `pagehide`. It is **not** dropped on `visibilitychange` or `blur`, because the sender backgrounds the tab to make the call. The string itself can't be zeroed (premise 5); the normalized phrase bytes were already zeroed after derivation (eng re-run correction). The footer copy becomes "Your draft was wiped. The phrase is wiped when you leave this screen." The message draft is still wiped immediately on sealing. After Reply sealed (the phrase is the reused opening phrase), the box is titled "Same phrase as the message you opened", with a muted line "They already know it. No call needed." (eng re-run ROV9b).
- **Exit from Open (eng re-run ROV5).** Under the recipient reload notice and in paste mode, a secondary button "Write a new message" calls `replaceState(null, '', '/')` and goes to an empty Compose.
- **Sender reload notice (eng re-run ROV3).** On entering Sealed, `replaceState({ sealedSender: 1 }, '', '/')` (non-secret). If the app boots with that marker (reload, or restore after discard), or receives `pageshow` with `persisted` after the phrase was removed, it shows Compose with a neutral box: "The phrase was cleared when this page reloaded. If you already sent the link, it can't be opened. Seal the message again and send the new link." The marker clears on New message and on sealing again.

### R2-1 — feasibility (blocking)

**Problem**

> The new CSP adds connect-src 'none' and says the real header comes from Cloudflare _headers, which 'also covers the KDF worker script', so it is applied to worker scripts. A service worker is governed by the CSP delivered with its own script response, and connect-src controls fetch() inside workers, including cache.addAll() and any network fallback in the fetch handler. If the same _headers rule covers /sw.js, the service worker cannot precache anything, and the offline E2E and the installability check (SW controlling the page) fail.

**Remedy**

> Give /sw.js its own header rule with connect-src 'self' (or omit connect-src for that path), keep connect-src 'none' for documents and the KDF worker, list both rules in the design, and have the offline E2E run against the real _headers so a misapplied rule is caught.

### R2-2 — consistency (blocking)

**Problem**

> Constraints now define 'zero requests' as: after the load event, the page itself makes no network requests. But the KDF worker is created with new Worker(new URL(...)) on Seal or Open, after load, which fetches the worker script (and any chunks it imports). In the E2E that opens the link 'with service workers blocked', this is a real network request after load, so the 'zero page-originated requests after load' test and the Open screen's 'zero network requests after loading' copy fail. Even when the SW is controlling, the request still shows in the network log as served by the ServiceWorker.

**Remedy**

> Either create the worker eagerly at boot and make sure its script (and imports) is fetched before load (for example, start the worker in the boot module and wait for its ready message before the load event finishes, or preload it), or extend the definition and the E2E to explicitly allow the same-origin worker-script fetch. Then make the copy match.

### R2-3 — completeness (blocking)

**Problem**

> The new estimator credits any non-EFF token 4 bits per character, up to 20 bits, and applies the repeat rule only to EFF words. Common human-chosen words that are not on the EFF list (names, places, 'password', 'qwerty') therefore score double what a list word scores: 'jennifer london soccer' = 3 × 20 = 60 bits and 'qwert qwert qwert' = 60 bits, both passing the 50-bit gate. The custom label then shows '≈ 60 bits'. This is the same gameable-estimator risk R1-4 asked to close (repeated and patterned words passing), now through non-dictionary tokens.

**Remedy**

> Apply the repeat rule to every token, and score non-dictionary alphabetic tokens no higher than dictionary words (or check them against a common-words/names list and credit them low), so a custom phrase needs real entropy to pass.
